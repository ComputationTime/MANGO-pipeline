Architecture and data flow

The workflow is a sequence of file contracts. Each stage knows the format of its inputs and outputs, but does not need to know every implementation detail upstream.

The complete path

Zenodo archive→standardized.csv→records.csv→embeddings→trained runs→test predictions / designs→metrics→figures

Repository layers

LocationResponsibility
config/config.yamlScientific and execution settings. Overlay files such as gpu.yaml and smoke.yaml change a bounded subset.
workflow/SnakefileLoads the configuration and includes the active rule modules.
workflow/rules/*.smkDeclares the file graph: inputs, outputs, resources, environments, and scripts.
workflow/scripts/Implements parsing, embeddings, model operations, metrics, and plotting.
workflow/envs/Defines isolated Conda environments for incompatible dependencies.
artifacts/Holds downloaded data, weights, caches, embeddings, models, logs, and results. It is not source code.

Trace one record

  1. The fetch rule downloads the pinned SAbDab2 archive and writes a readiness marker only after the expected split table exists.
  2. The standardizer converts SAbDab2-specific columns into stable names such as id, pdb_path, expected sequences, chain identifiers, cluster, and source split.
  3. The processing checkpoint filters invalid records, resolves sequences from metadata/structure, assigns entire clusters to train, validation, or test, and writes records.csv.
  4. For every kept identifier, an antigen embedder writes a tensor. Separately, AbLang2 writes a light-only context tensor. Both are indexed by split and record identifier.
  5. The training script loads both tensors, shifts the known heavy sequence into next-token training targets, and optimizes one model for that antigen representation.
  6. Evaluation measures likelihood on train, validation, and test. Prediction reconstructs a heavy chain for test records. Generation samples multiple heavy chains for a diverse target set drawn from held-out clusters.
  7. Analysis selects the same deterministic number of successful designs per target and model, applies independent scorers, and produces figures plus the exact CSV rows behind each figure.

Why a checkpoint is necessary

Before processing runs, Snakemake cannot know which structures survive filtering or which split each identifier belongs to. process_records is therefore a checkpoint. After it writes records.csv, helper functions read that table and expand embedding/generation jobs for the actual records.

Fine-grained versus batch embeddings

Fine-grained mode creates one Snakemake job per record, which is convenient for incremental local work. GPU study mode uses batch rules: one process loads a large pretrained model once, loops over all relevant records, writes the same per-record tensor files, and then writes a completion marker. This avoids reloading large weights thousands of times.

Run identity and reproducibility

A trained run is named <embedder>__<hash>. The hash covers the dataset, filters, embedding configuration, embedder parameters, model settings, weight configuration, and experiment seed. Changing scientific state creates a new directory instead of silently overwriting an incompatible model. Execution-only settings such as plotting cadence are excluded.

Failure isolation

The supported GPU launcher invokes Snakemake separately for each antigen embedder. A Conda solve, authentication gate, weight download, or scientific job failure in one method does not prevent later methods from being attempted. A partial JSON/CSV report records successful metrics and the first missing stage. Strict cross-model figures are produced only when all requested methods finish.
